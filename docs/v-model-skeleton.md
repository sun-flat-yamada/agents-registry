# 🧭 V字モデル骨格と選定基準 (V-Model Skeleton & Selection Criteria)

本レジストリは「最新のものを雑多に集める」ことを目的にしません。**ソフトウェア開発の V字モデルの工程**を骨格（枠 = slot）とし、各枠に**ベストを 1 つだけ**登録します。より良いものが見つかれば、その 1 つを更新または入れ替えます。

現在どの枠に何が入っているかは [`registry.yml`](../registry.yml) が正です。

---

## 1. 枠の一覧

```text
 V1 要求定義 ─────────────────────────────── V8 受入テスト
    V2 基本設計 ───────────────────────── V7 システムテスト
       V3 詳細設計 ─────────────────── V6 結合テスト
             V4 実装 ─────────── V5 単体テスト

 横断: X1 コードレビュー / X2 セキュリティ
```

| ID | 工程 | 対になる検証 | この枠の役割 |
| :--- | :--- | :--- | :--- |
| V1 | 要求定義 | V8 | 曖昧な要望を、検証可能な要求（受入基準つき）に落とす |
| V2 | 基本設計 | V7 | システム構成・境界・主要な技術判断を決め、ADR 等に残す |
| V3 | 詳細設計 | V6 | モジュールのインターフェース・データ構造・手順を実装可能な粒度で設計する |
| V4 | 実装 | V5 | 設計に沿って、小さく検証しながらコードを書く |
| V5 | 単体テスト | V4 | 関数・クラス単位の振る舞いをテストで固定する（TDD を含む） |
| V6 | 結合テスト | V3 | モジュール間・外部依存との接続を検証する |
| V7 | システムテスト | V2 | 実際に動くシステムを E2E で検証する |
| V8 | 受入テスト | V1 | V1 の受入基準に対して完成物を確認し、合否と根拠を残す |
| X1 | コードレビュー | — | 変更差分の正しさ・品質をマージ前に確認する |
| X2 | セキュリティ | — | 設計・実装・依存関係の脆弱性を検出し、対処方針を示す |

左右の対は「左の成果物が、右の検証の入力になる」ことを意味します。たとえば V1 が出す受入基準は、V8 がそのまま使える形でなければなりません。枠を選定するときは、対になる枠との受け渡しも確認します。

### 「1 つ」の単位

1 つ = **1 つの入口**（スキル、エージェント、コマンドのいずれか）です。入口が内部でサブエージェントや参照資料を使うことは構いません（例: X1 の `code-review` スキルは複数のレビュアーを束ねています）。同じ枠に入口が 2 つ並ぶ状態は作りません。

### 枠に入らないもの

- **レジストリ運用ツール**（`retrospective-harness`、`update-harness`、`meta-skill-manager` など）は、このレジストリ自体を保守するための道具です。残しますが、枠の 1 つには数えません。
- **開発外のもの**（会計、投資、料理、個人ワークスペースなど）は [`archive/non-dev/`](../archive/non-dev/) に退避し、配信対象から外しています。
- **置き換えたもの・どの枠にも入らない開発系のもの**は [`archive/dev-retired/`](../archive/dev-retired/) に退避しています。

## 2. 選定基準

候補は次の 6 つの観点で評価します。上から順に重視します。

1. **工程への適合**: その枠の役割を、毎回の開発で確実に果たせるか。特定のアプリや言語に依存しすぎていないか。
2. **出典の信頼性**: Anthropic 公式リポジトリ由来を第一候補とします。コミュニティ由来（例: `worldflowai/everything-claude-code`）は 2026 年初頭時点の情報のため、**今でも通用する考え方・テクニックだけ**を取り入れ、内容をそのまま持ち込みません。
3. **最新性**: 現行の Claude / Claude Code の機能（サブエージェント、スキル、フックなど）を前提にしているか。古いモデルや廃止された手順に依存していないか。
4. **移植性**: Claude Code をメインとし、GitHub Copilot CLI でも同じ定義から使えるか。
5. **検証可能性**: 出力が具体的で、対になる枠に渡せる形か。成功・失敗を判定できるか。
6. **安全性**: `scripts/security-audit.py` の監査を通るか。不要な権限や外部送信を要求しないか。

---

## 3. 登録・入れ替えのルール

- **新規登録**: 空の枠に候補を入れるときは、上記 6 観点の評価を PR に書きます。
- **入れ替え**: 現行より明確に良い場合だけ入れ替えます。PR には現行と候補の比較表（6 観点ごと）と、根拠となる出典 URL を載せます。差が小さい場合は現行を維持し、良い部分だけを現行に取り込む「改善」として扱います。
- **判断は人間**: 自動探索・自動生成された変更でも、マージは必ず人間が判断します。自動マージはしません。
- **記録**: 変更のたびに `registry.yml` の `selected`（出典・理由）と `last_reviewed` を更新します。

### `registry.yml` の status

| status | 意味 |
| :--- | :--- |
| `empty` | まだ何も登録されていない |
| `provisional` | 既存資産から暫定的に割り当てたもの。公式ソースとの比較は未実施 |
| `selected` | 選定基準に沿って比較し、ベストとして選んだもの |
